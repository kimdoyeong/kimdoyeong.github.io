# FMS

FMS는 File Management System의 약자로, 내가 필요로 해서 개발한 동영상 관리 프로젝트다. 내 NAS에 있는 영화, 애니메이션 혹은 유튜브 영상들을 쉽고 빠르게 찾기 위해서 개발되었다.

![FMS 1](/images/fms/1.png)

![FMS 2](/images/fms/2.png)

## 주요 기능

- 동영상 썸네일 생성 (동영상의 일부를 잘라 하이라이트처럼 만듦)
- 태그 기능
    - 시간 지정 태그 기능
- 쇼츠 생성 기능
- 유튜브 영상 반입 기능
- 자막 번역 기능
- 음성 전사 기능

내가 FMS를 만들게 된 계기는 간단하다. 내가 필요로 했던 서비스였기 때문이다. 나는 FMS와 비슷한 프로젝트를 2019년 즈음부터 계속 시도해왔는데, 어떤 프로젝트는 1년간 지속되긴 했지만 결국 변덕이라던지 이런저런 이유로 버려지기 일쑤였다.

나의 변덕의 이유 중에 가장 큰 것은 설계가 마음에 들지 않는다는 점이었다. 나는 FMS의 선행 프로젝트들을 내가 배운 것을 적용하는 계기로 사용해왔고, 배운 것이 쌓여갈수록 코드 보는 눈이 높아져 버린 것이었다!

이번에도 그러한 이유로 FMS를 만들게 되었다. 내가 어떤 것을 배웠고, 또 어떤 것을 적용했는지 이 글을 통해서 소상히 밝히고자 한다.

# 제품 기획

최근 내가 읽은 책이 있다.  『AI 시대의 엔지니어링 전략』 (한빛미디어, 2026)이라는 책을 읽었다. 사실 나는 원제가 이 책의 의미를 더 잘 담고 있다고 생각한다. (원제는 The Product-Minded Engineer이다.)

이 책은 개발자가 구현에만 집중하는 것이 아니라 제품 기획에 있어서도 관심을 가져야 한다고 말하고 있다. 이러한 프로덕트 사고는 좋은 엔지니어가 되기 위해서 필수적이다. 요구사항대로 기능을 구현했더라도 사용자의 문제가 해결되지 않았다면 그것은 좋은 제품이라고 할 수 없다. 따라서, 엔지니어링의 궁극적인 목표는 사용자의 문제를 해결하는 것이다. 그렇기 때문에 누가 어떤 상황에서 기능을 사용하고 무엇을 얻어야 하는지를 생각해야 한다.

그렇다면 “누가 어떤 상황에서 사용하고, 무엇을 얻어야 할까”를 다루는 것이 바로 시나리오이다. 시나리오는 페르소나, 동기, 시뮬레이션으로 구성된다.

- 페르소나: 사용자가 가진 배경, 지식, 경험과 제약
- 동기: 지금 해결하려는 진짜 문제
- 시뮬레이션: 기능을 발견하고 목표를 달성하기까지의 구체적인 과정

예를 들어 보자. ‘나’는 대학생으로 (페르소나), 필기 시험을 준비하는 데에 어려움을 겪고 있다. 특히, 풀어볼 문제가 부족하다고 생각하고 있다.(동기) 나는 평소에 자주 쓰는 PDF 노트 앱을 켰다. 그리고 무언가 반짝이는 아이콘을 발견했다. 나는 그것을 눌러 본다. 그러자 채팅 창이 나타난다. 나는 이것이 요즘 유행하는 AI 채팅임을 알고 있다. (과제를 할 때 많이 썼기 때문이다.) 나는 채팅창에 “이 pdf를 기반으로 문제를 생성해줘”라고 입력한다. 그러자 잠시 기다리라는 문구가 뜨더니, 이내 채팅으로 문제가 올라오기 시작한다. 나는 문제를 여러 종류로 풀어보면서 시험을 대비할 수 있었다. (시뮬레이션)

단순히 ‘노트 기반 생성형 AI’보다는 훨씬 문제가 잘 드러난다. 단순히 기능을 기술했다면, 기술을 개발하는 사람들 사이에서 소통의 문제가 생겼을 것이다. 예를 들어 누군가는 이 기능을 단순히 ‘요약’으로만 알았을 수도 있다.

이러한 시나리오 중에서, 제품의 핵심을 가장 잘 담고 있으며 길잡이가 될 시나리오가 바로 북극성 시나리오이다. 나는 FMS의 북극성 시나리오를 이렇게 네 가지로 나눠 썼다.

1. 동영상을 빠르게 훑어보고 싶은 사람 (’김몰라’)
2. 동영상을 검색하고 싶은 사람 (’박검색’)
3. 동영상을 분리해서 저장하고 싶은 사람 (’최분리’)
4. 동영상을 정리하려는 사람 (’이묶음’)

참고로 이름은 직관적으로 들어오도록 짓는 것이 좋다는 조언이 있었다. 이렇게 북극성 시나리오를 쓰고 나니 어떤 기능을 추가할지 명확해졌다. 이렇게 ‘쇼츠 기능’이 추가되었다.

혼자 쓰고 개발하는 프로젝트인데 이렇게까지 할 필요가 있냐고 말할 수도 있을 것 같다. 그러나 나는 AI를 활용하는 일을 AI와 소통하는 일로 생각하고 있으며, 따라서 실제 조직에서 사용하는 스킬들이 AI 활용에 있어 도움이 된다고 생각하고 있다.

AI를 활용할 때 가장 중요한 덕목은 표현하는 것이라고 생각한다. 머릿속의 암묵지를 명시적인 글로 바꾸는 연습이 필요하다.

# 기술 선택

개인 프로젝트이므로 기본적으로 ‘가장 익숙한가’를 고려할 수 밖에 없다. 그래서 프론트엔드에는 내가 가장 오래 다뤄왔던 React를 적용했다. SSR은 별로 필요하지 않다고 생각했기 때문에 Next.js 등은 사용하지 않았다. React로 빌드해 곧바로 API 서버에 탑재한다.

사실 요즘은 React를 굳이 골라야 하는지 고민된다. React가 선택되는 이유의 상당 부분은 개발의 편의성에 있다고 생각하기 때문이다. 그렇지만 이제는 AI가 코딩을 전담한다. 성능이나 번들 크기만을 보면 무조건 React를 선택해야 할 이유는 없다고 생각한다. React를 고르는 것은 어쩌면 관성적으로 하는 것이 아닌가 생각이 든다.

API 서버는 bun과 hono를 사용한다. bun은 node.js에 비해 훨씬 빠르다. 이 프로젝트는 동영상을 다루는 프로젝트이기 때문에 퍼포먼스도 어느 정도 중요했다.

API 서버에는 계층형 아키텍처와 도메인 개념별로 나눈 모듈형 아키텍처를 채택했다. AI는 경계를 나눌 수록 좋은 품질의 코드를 생성한다고 경험적으로 알고 있었기 때문이다. (Garbage in, Garbage out) 경계가 분명하다면 AI가 건드려야 할 범위도 분명하게 정해지고, 나중에 수정을 할 때도 그 범위가 작아진다. (수정가능성을 높이는 것은 SWE에게 있어 중요한 목표이다.)

그리고 나는 두 가지 문서를 만들었다.

- **도메인 모델 문서**: 개념을 AI에게 이해시키기 위해 따로 만들었다. 이 문서를 위해 AI와 꽤 오랜 시간 대화했다. 『도메인 주도 설계』를 읽고 적용한 방식이다.
- **안티패턴 문서**: 하지 말아야 할 것을 명시해 경계를 엄격하게 관리한다.

그리고 TDD를 채택했다. TDD는 결과를 빠르게 확인하고 고치는 데 강하다. 옛날 모델들은 테스트를 처음부터 이상하게 만드는 때가 많았지만 요새 모델들은 테스트도 잘 만들고, 지시하지 않아도 TDD를 적용한다. TDD는 리팩터링 할 때도 굉장히 유용하다.

소프트웨어 엔지니어링을 다룬 고전들이 AI 활용에도 그대로 도움이 된다는 점이 흥미로웠다.

# 제약 사항

## 혼자 사용한다

사용자가 나 하나이므로 파일 소유권 같은 귀찮은 문제는 따지지 않는다. 권한 모델이 빠지는 것만으로도 설계가 크게 단순해진다.

## 느린 서버

서버 사양은 Intel N100, 메모리 16GB, 저장공간 512GB다. 실시간 트랜스코딩은 꿈도 못 꾼다. 게다가 이 서버에서 FMS만 돌아가는 것도 아니다. 그래서 자원을 최대한 덜 먹는 쪽으로 설계했다.

- **ffmpeg는 배치로**: 실시간이 아니라 배치 작업으로 처리한다.
- **쇼츠는 가볍게**: 쇼츠는 자동으로 생성하되 머신러닝은 쓰지 않는다. 화면, 소리, 자막을 기준으로 빈 화면만 걸러낸다.

## 셀프 호스팅

푸시하자마자 바로 쓸 수 있으면 좋겠다는 바람이 있었다. 그래서 Forgejo로 자동 릴리즈를 구성했다. 코드를 올리면 곧바로 내 서버에 반영된다.

# 마치며

나는 최근 프로그래밍 그 자체가 아닌 소프트웨어 엔지니어링에 관심을 가졌다. 그런 부분이 프로젝트를 하면서 많이 드러난 것 같다. 아마도 소프트웨어 엔지니어링을 공부하는 일은 AI 시대에도 큰 도움이 될 것이라고 생각한다. 소프트웨어 엔지니어링은 협업에 대해 다루기 때문이다.

다만 바람이 하나 있다면, 이렇게 혼자 사용하는 프로젝트가 아닌 여러 사람이 사용하는 프로젝트를 만들고 피드백을 받고 싶다는 것이다. 그렇게 해야 내가 배운 것을 100% 적용할 수 있었을 텐데 말이다.

다음에는 여러 사람이 사용하는 프로젝트를 해 보아야겠다.
